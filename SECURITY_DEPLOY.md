# Технические исправления review — 15.09.2026

## Что изменилось

- Общие атомарные лимиты запросов и отправок в `core.AbuseBucket` (основная БД).
  Redis не нужен. LocMem остаётся только кешем представления. IP/email в ключах
  не сохраняются открыто: ключ — SHA-256. Счётчики действуют между процессами
  и после перезапуска. При недоступной БД операция не проходит без ограничений.
- Резервирование квот выполняется до SMTP. Попытки, в том числе неуспешные,
  расходуют квоты. При отказе поздней проверки ранние резервы не возвращаются:
  это намеренная консервативная защита от параллельного превышения.
- Дубликаты контактных сообщений за 30 минут не записываются повторно даже при
  выключенной почте. Общая проверка охватывает главную, about и футер. Honeypot
  `website` возвращает обычный ответ об успехе без сохранения/SMTP. CAPTCHA позже.
- Заказ и позиции создаются одной транзакцией. Уникальный HMAC в
  `Order.checkout_fingerprint` привязан к session_key и серверному ключу формы.
  IP больше не является удостоверением владельца. Повтор в другой сессии
  не предоставляет доступ. Повтор с новым IP в исходной сессии допустим.
  Первый POST требует предварительно открыть checkout; произвольный ключ
  отклоняется. Записи защиты повторов живут вместе с заказом, без TTL кеша.
- Вход admin и все POST password-reset ограничены в middleware (включая
  невалидные формы). Обычная форма входа сохраняет свой ограничитель.
- SMTP timeout по умолчанию 8 секунд. Сбой SMTP не удаляет контактное сообщение
  или заказ. Очередь автоматических повторов пока не добавлена.
- Подключён django-otp с TOTP и одноразовыми резервными кодами. Обязательность
  второго фактора включается после настройки устройства (`ADMIN_OTP_REQUIRED=1`).
- Backup читает **эффективный settings.DATABASES**, а не разбирает `.env` shell-ом.
  SQLite копируется через Python backup API, включая WAL; PostgreSQL через
  pg_dump с настроенными host/port/user/database. Пароль только в окружении
  subprocess, не в аргументах/логе. Неуспешная копия не заменяет успешную.

## Обновление VPS

Работа выполнена в локальном репозитории. Эти действия на VPS ещё не запускались.

1. Сохранить резервную копию текущей БД перед обновлением. При первой установке
   этой версии старый `update-safe.sh` ещё не содержит исправления: отдельно
   проверить, что резервируется фактическая база из Django settings. Не полагаться
   на старое значение `POSTGRES_DB` по умолчанию при нестандартной конфигурации.
2. Установить requirements и выполнить `python manage.py migrate` (новая core
   migration 0023 и миграции django-otp). Остановить/перезапустить старые workers
   после миграций; обычный update.sh уже выполняет migrate перед restart.
3. Выполнить `python manage.py check --deploy` в production-окружении.
4. Запланировать `python manage.py cleanup_abuse` ежечасно через cron под
   пользователем приложения с его venv и рабочим каталогом проекта. Без очистки
   активные ключи переиспользуются, но неактивные истёкшие строки накапливаются.
5. Проверить свежую резервную копию командой
   `python manage.py backup_database --directory /var/backups/creativesphere --keep 30`.
   Для каталога root выполнять от root; права каталога 0700, файлов 0600.
   У пользователя запуска должны быть действующие права подключения к БД.
   Для PostgreSQL нужен совместимый `pg_dump`. Хранить копию также вне VPS;
   периодически проверять восстановление в отдельную тестовую БД.

### Nginx для уже установленного сайта

Первичный deploy-vps.sh генерирует лимит сам. На существующем HTTPS-сайте
**не перезапускать установщик ради этого изменения**. Добавить один раз в `http`
контекст (вне server; например, отдельный `/etc/nginx/conf.d/creativesphere-limits.conf`):

```nginx
map $request_method $creativesphere_post_ip {
    default "";
    POST $binary_remote_addr;
}
limit_req_zone $creativesphere_post_ip zone=creativesphere_post:10m rate=2r/s;
```

В существующий `location /`, который проксирует Django:

```nginx
limit_req zone=creativesphere_post burst=10 nodelay;
limit_req_status 429;
```

Проверить `sudo nginx -t`, затем `sudo systemctl reload nginx`. Не определять
map/zone повторно, если они уже созданы установщиком. Это грубый лимит POST;
точные лимиты форм сохраняются в Django. При добавлении CDN сначала правильно
настроить доверенные proxy IP; Gunicorn должен остаться на 127.0.0.1.

### Подключение второго фактора

1. После migrate оставить `ADMIN_OTP_REQUIRED=0` на время настройки.
2. Войти в Django admin как superuser; в TOTP devices создать **своё** устройство,
   перенести ключ/QR в личный аутентификатор. Не публиковать ключи в репозитории,
   логах или переписке. Настроить устройства для остальных администраторов.
3. Создать резервный одноразовый код командой
   `python manage.py addstatictoken <username>` в приватной консоли и сохранить
   его в менеджере паролей. Код выводится в этой консоли; не запускать через CI.
4. Выставить `ADMIN_OTP_REQUIRED=1` в `.env`, перезапустить Gunicorn, проверить
   новый вход паролем + кодом, пока сохранён SSH-доступ для восстановления.
   Обычная пользовательская сессия без OTP больше не откроет admin.
5. При потере устройства создать новый одноразовый резервный код через SSH,
   войти с ним и заменить устройство. Не отключать защиту ради восстановления.

Второй фактор защищает Django admin; пользовательский профиль остаётся отдельным
интерфейсом с существующими правами. Если потребуется обязательный OTP для всех
редакторских операций в профиле, это отдельное расширение политики.

## Проверки

`python manage.py test core` включает регрессии в tests_security.py: межпроцессные
квоты на отдельной временной SQLite, владение заказом, откат транзакции, уникальный
ключ, OTP login, SMTP timeout/failure budget, формы-ловушки, SQLite WAL backup,
параметры pg_dump. Nginx и PostgreSQL на реальном VPS проверяются при развёртывании.
